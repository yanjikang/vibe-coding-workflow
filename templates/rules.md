# 项目规范（rules.md）

> **用法**：分两步生成——窗口 1 让 AI 写"通用版"（目录/命名/风格），窗口 2 结合本项目定制。
> 开启任务模式前，AI 必须先读本文件。**严禁事项是活文档**：修 Bug 循环中 AI 重复犯错时立即追加一条。
>
> **追加触发条件**（来自工作流六·Rules 反哺）：同一错误**重复出现第 2 次**，或暴露出一条系统性约定缺失时才追加。
> 不是每个小 Bug 都写禁令——Rules 臃肿了 AI 也会抓不住重点。

## 技术栈约束

- 语言/框架/构建工具以 `plan.md` 第 2 节的锁定版本为准，禁止擅自升级或引入新依赖
- 只用社区语料最丰富的主流写法，禁止冷门库、禁止实验性 API
- 引入任何新依赖前，先说明理由并等待确认

## 目录与命名

- 目录结构遵循 `docs.md` 第 2 节约定，禁止自创层级
- 组件文件名 〔PascalCase〕，工具函数 〔camelCase〕，常量 〔UPPER_SNAKE〕
- 单文件超过 〔300〕 行必须拆分（对应工作流 Step 16 结构瘦身判断）

## 代码风格

- 〔TypeScript 严格模式，禁止 any〕
- 函数保持单一职责，超过 〔50〕 行考虑拆分
- 错误处理：不允许空 `catch`，报错必须带上下文信息

## 严禁事项（踩坑沉淀区）

> 以下为示例，每条都应来自真实踩坑，格式：❌ 禁令 + 正确做法。

- ❌ 禁止在组件内直接写 `fetch`，一律走 `src/api/request.ts` 统一封装
- ❌ 禁止使用 `any` 类型；接口返回必须定义 interface
- ❌ 修改组件前必须先读 `progress.md`，确认不重复开发已完成功能
- ❌ 禁止在未确认数据库表结构前编写查询语句

## 沟通与执行约定

- 修 Bug 时必须基于**完整报错日志**定位，禁止凭猜测打补丁
- 每完成一个可验证的功能点，主动提示"可以 git commit 存档了"
- 同一 Bug 修复尝试超过 3 次仍失败时，主动建议：回滚 + 归因总结 + 换窗口（熔断流程）
